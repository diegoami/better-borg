## Step 1 - the C-fidelity check (rule 2): verdict FAITHFUL

Both structural halves of the diagnosis were checked against the local 4.2.6
source at `neo-angband/reference/src/borg/`. **The port matches the C on both
halves; the C behaves the same.** The wrong call is upstream 4.2.6 behaviour,
not a port defect, so the fix is an improvement (CHOICE), fork-only.

### Half 1 - stage order: caution's back-away runs BEFORE the attack stage, in the C too

- `borg-think-dungeon.c:1540` - `if (borg_caution()) return true;` ("Try not
  to die"). `borg_caution` (`borg-caution.c:799`) ends in the *** Back away
  *** section at `borg-caution.c:1664` (outer gate `1673-1677`:
  `pos_danger > avoidance * 4 / 10 && !nasty && !borg.no_retreat ... &&
  CURHP < 500`), so whenever back-away fires, it pre-empts everything below.
- `borg-think-dungeon.c:1596` - `if (borg_attack(false)) return true;`
  ("Attack monsters") - **56 rungs of ladder after caution**, with only
  light-maintenance, town-recovery, wear-stuff and anti-summon-corridor
  rungs between them, none of which attacks.
- (A second `borg_attack(false)` at `borg-think-dungeon.c:896` and a
  `borg_attack(true)` at `:941` live inside munchkin mode and the
  boosted-bravery subset respectively - different ladders, not this order.)
- Port: `src/think-ladder.ts:627` (`borgCaution`, cited `:1540`) runs before
  `src/think-ladder.ts:675` (`borgAttack(ctx, false)`, cited `:1596`);
  `borgBackAway` (`src/fight/caution.ts:648`) with the same outer gate at
  `:659-666` is called from inside `borgCaution` at `caution.ts:594`.
  **Same order, same pre-emption: FAITHFUL.** While adjacent-and-hurt, 4.2.6
  never evaluates the thrust either.

### Half 2 - the bounce guard's health gate: same gate, same polarity, in the C too

`borg-caution.c:1725-1732` (inside back-away; the same pattern also guards
the strategic-retreat scan at `:1457-1464` and its walk simulation at
`:1525-1533`):

```c
if ((borg.trait[BI_CURHP] >= borg.trait[BI_MAXHP] * 7 / 10
        && ((track_step.num > 2
             && (track_step.y[track_step.num - 2] == y
                 && track_step.x[track_step.num - 2] == x
                 && track_step.y[track_step.num - 3] == borg.c.y
                 && track_step.x[track_step.num - 3] == borg.c.x))))
    || borg.time_this_panel >= 300)
    continue;
```

The health test `CURHP >= MAXHP * 7 / 10` ANDs with the oscillation match
(the comment above it says "Try to avoid pillar dancing if at good health"),
so below 70% hp the bounce detection is DISARMED - exactly when an
oscillation turns lethal. Port: `src/fight/caution.ts:694-701` - identical
structure and polarity (`CURHP >= idiv(MAXHP * 7, 10) && ...`, then
`if (bouncing || timeThisPanel >= 300) continue`). **FAITHFUL.**

(The strategic-retreat section itself - `borg-caution.c:1420-1660` - is not
ported at all; that is a pre-existing porting scope decision recorded in
caution.ts's header, unchanged by this task.)

### The kill-shot numbers (the chooser's own, for step 2)

The C's attack chooser has the one-hit idiom verbatim:
`borg-fight-attack.c:1330-1331` - `if (d >= kill->power) d = 2 * d;` ("Extra
'bonus' if attack kills"), where `d` is the thrust damage estimate
(`borg_thrust_damage_one`, `borg-fight-attack.c:100`; port
`src/fight/attack.ts:136`) and `kill->power` is the monster's CURRENT
estimated hp - upstream computes it from the health-bar percent
(`borg-flow-kill.c:171-173`: `kill->power = (maxhp * pct) / 100`), the port
reads the same current hp at `src/perceive.ts:356`. So "expected damage at
or above the kill's remaining hp" is `borgThrustDamageOne(ctx, i) >=
kill.power` with the chooser's own numbers on both sides.

## Step 2 - the fix (mixed: each half goes to its right home)

1. **The kill-shot appraisal before caution's retreat commits** - CHOICE,
   fork-only, `FORK:`-marked (`src/fight/caution.ts`, `borgBackAway`, after
   the early-outs, before the direction loop): when an ADJANTENT,
   currently-seen monster would die to one average thrust
   (`borgThrustDamageOne >= kill.power`, the chooser's idiom above), and the
   chooser's own hard gates would let the thrust fire (not afraid; not the
   town-asleep case), back-away yields (returns null) so the ladder's attack
   stage - 4.2.6's own chooser, unmoved - takes the thrust. Attacking the
   one-hit blocker IS the retreat: it removes the danger back-away is
   fleeing and opens the grid the flow wants. The appraisal changes no
   command itself; it only stops back-away from pre-empting the chooser.
2. **The bounce guard** - MIXED, found while implementing:
   - **Port DEFECT (fixed to match the C, no fork mark)**: `track_step` was
     never written anywhere in the port - only wiped - so the bounce guard
     read an empty track at ANY health and could never fire (the same
     emptiness blinds `borg_happy_grid`'s recently-stepped check,
     flow-misc.ts). The C records `borg.c` into `track_step` after every map
     update (`borg-update.c:2466-2475`, size 100 at `borg-flow.c:1265`,
     compact-at-75 shift). Restored verbatim in the decide pass
     (`src/controller.ts` step 3a, right after `perceive`).
   - **CHOICE, fork-only, `FORK:`-marked** (`src/fight/caution.ts`): drop
     the `CURHP >= MAXHP * 7 / 10` conjunct from the bounce test, so an
     oscillating grid is refused at ANY health. Upstream's gate exists to
     avoid pillar-dancing "at good health" (its own comment); under
     pressure it disables the escape from a lethal interlock. With the
     guard armed, one back-away/flow cycle exhausts the bounced grid and
     the borg stands, re-routes, or fights instead of looping forever.

**No upstream ask from this task.** The wrong-port branch of rule 3 never
opened: both diagnosed halves are faithful, and the one true defect
(track_step) is a gap in OUR port, not in upstream's code - upstream
maintains track_step correctly (borg-update.c:2466). The dupe-check
obligation belongs to the wrong-port branch and does not trigger.

**Found and fixed beside them** (step 3 could not run without it): the
postmortem dossier's fixed 33x17 window crashed with
`features.get(undefined)` when a rung boundary sat near the level edge -
core's `knownFeat` indexes the known map with no bounds check

diverged replay did, immediately. Out-of-bounds now renders as unknown
terrain, restoring B29's documented "a diverged replay still writes its
dossiers" behaviour (its semantic choice 5).
