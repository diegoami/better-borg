- **Where valuation scores surface** (the brief's open question, answered):
  the engine's agent seam (`AgentController`) is a frozen view-in/command-
  out boundary and exposes NO scores - the host never ranks candidate
  actions for a mod. The valuations live in this port's own decision code,
  and the one per-decision numeric ranking of candidate ACTIONS is the
  best-attack chooser (`borgAttack`'s scan over BF_* methods,
  src/fight/attack.ts). The think ladder is priority-ordered (first
  rung wins - "ties" do not apply), and the item valuations are per-item
  thresholds, not per-decision rankings. Ties are read at their source,
  mod-side; no engine-side read was needed and none was added.

- **The uncertainty signal, exactly**: (a) *valuation-tie* - the chooser's
  top two method scores within 5% (relative; scores are expected-damage
  numbers that scale with the character), requiring command IDENTITY (the
  recorded valuation describes the attack that was committed, not a
  lookalike command); an exact tie is the purest case - the enum order
  alone broke it. (b) *known-world-gap* - a direction command whose aimed
  grid carries no BORG_MARK on the Borg's OWN map (terrain it has never
  observed). Rare, and honestly so: flow routes through known grids.
  Both journaled with turn/depth/hp/position/candidates/chosen; the
  journal keeps the last 100 points beside the raw total.

- **Where the points land** (the on-death aggregation): the restart loop's
  graveyard write carries them INTO the archived install entry (the
  journal's optional dossier parameter - one write, no second
  read-modify-write over the shared slot), so a later page reads "where I
  was unsure" beside the report's own facts. The harness's observing
  controller collects the same points beside its census, and runs.json
  carries them additively (`unsure`: total + tail; the schema id stays
  `better-borg/runs@1`, rule 8; records before B27 carry no key).
